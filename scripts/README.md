# NGK2027S 申込の自動処理

Googleフォームに届いた申し込みを受け付け、Discord へ流し、承認されたら申込者へ連絡してロールを付ける。

人が手を動かすのは、Discord の投稿に `:yosasou:` を2つ付けるところだけ。

来年の運営メンバーと、この仕組みを初めて触るスタッフに向けて書いた。

## 言葉

この文書で使う言葉を先に決めておく。

| 言葉 | 意味 |
|---|---|
| Apps Script | Google のサービス。スプレッドシートに紐づけて動かす小さなプログラム |
| コンテナ | スタッフのPCで動かし続けるプログラム。Docker を使う |
| 申込投稿 | 申し込みが届いたときに、スタッフ専用チャンネルへ出る投稿 |
| 承認 | 申込投稿に `:yosasou:` が2人分付くこと |
| 管理列 | スプレッドシートの右端に自動で足される列。どこまで処理したかを時刻で記録する |

Discord では同じ絵文字を1人1回しか付けられない。
だから `:yosasou:` が2つ付いていれば、2人が見て承認したことになる。

使う絵文字は6つ。どれも Discord のリアクションとして投稿に付ける。

| 絵文字 | 誰が付けるか | 意味 |
|---|---|---|
| `:yosasou:` | スタッフ | 承認してよい。2つで承認が成立する |
| `:horyu:` | スタッフ | 保留。付いている間は `:yosasou:` が2つあっても進まない |
| `:mail_done:` | 自動 | 採択メールを送った |
| `:discord_done:` | 自動 | 一般向けチャンネルへ投稿した |
| `:role_done:` | 自動 | ロールを付けた |
| `:ok_done:` | 自動 | 申込者が確認した |

`:horyu:` を外すと、次の回から進む。
申し込みを断る仕組みはない。不採択の連絡はスタッフが手で行う。

## 3つのフォームと承認するもの

フォームは3つ。承認するものは4種類ある。
LT発表申込フォームの中で、申込者が「申込み種別」を選ぶため。

| フォーム | 承認するもの | 承認したら付けるロール |
|---|---|---|
| LT発表申込 | 一般LT | 一般LT登壇者/2027S |
| LT発表申込 | コミュニティLT | コミュニティ/ALL、コミュニティ/2027S、コミュニティLT登壇者/2027S |
| LT発表申込 | スポンサーLT | スポンサー/ALL、スポンサー/2027S、スポンサーLT登壇者/2027S |
| コミュニティ参加申込 | コミュニティ参加 | コミュニティ/ALL、コミュニティ/2027S |
| 企業スポンサー申込 | 承認しない | 付けない |

`/ALL` は年をまたいで残すロール。`/2027S` はその年だけのロール。
来年は `/2027S` のロールを作り直し、`env.example` と `.env` のIDを差し替える。

## LT発表申込とコミュニティ参加申込の流れ

左の列は誰が動くか。括弧の中は、その処理が動く間隔。

```
申込者がフォームを送信
      │
      ▼
Apps Script           受付番号を振る (LT-001)
(送信のたび)          申込者へ受付メールを送る
      │
      ▼
コンテナ              スタッフ専用チャンネルへ投稿する
(5分おき)             申し込み内容が一覧で出る
      │
      ▼
スタッフ              投稿に :yosasou: を2つ付ける    ← ここだけ人の仕事
                      :horyu: が付いていると進まない
      │
      ▼
コンテナ              承認を検知して記録する
(5分おき)
      │
      ▼
Apps Script           申込者へ採択メールを送る
(1分おき)             Discord の招待リンクを載せる
      │
      ▼
コンテナ              申込投稿に :mail_done: を付ける
(5分おき)             申込者のDiscordアカウントを名前で探す
                      一般向けチャンネルへメンション付きで投稿する
                      申込投稿に :discord_done: を付ける
                      ロールを付ける
                      申込投稿に :role_done: を付ける
      │
      ▼
申込者                一般向けチャンネルの投稿に 🆗 を付ける
      │
      ▼
コンテナ              確認済みとして記録する
(5分おき)             申込投稿に :ok_done: を付ける
```

最後から2つ目のまとまりは、1回の実行で続けて行う。
メンションとロール付与の間に待ち時間は入らない。

申込者がまだ Discord サーバーに居ないときは、申込者を探すところで止まって参加を待つ。
採択メールで初めて招待リンクを送るので、この時点で未参加なのはふつうのこと。
スタッフ専用チャンネルに1回だけ知らせを出し、以降は黙って待つ。

## 企業スポンサー申込の流れ

```
申込者がフォームを送信
      │
      ▼
Apps Script           受付番号を振る (SPONSOR-001)
(送信のたび)          申込者へ受付メールを送る
      │
      ▼
コンテナ              スタッフ専用チャンネルへ投稿する
(5分おき)             請求先は出さない。スプレッドシートで見る
      │
      ▼
ここで終わり。あとはスタッフが手で連絡する
```

企業スポンサーには承認の仕組みがない。金額と条件が申し込みの時点で決まっているため。

## かかる時間

| どこからどこまで | 最大 |
|---|---|
| 申し込みから受付メールまで | すぐ |
| 申し込みからスタッフ専用チャンネルの投稿まで | 5分 |
| 承認から採択メールまで | 6分 |
| 承認からDiscordのメンションとロールまで | 11分 |

承認から6分は、承認の検知に5分、採択メールの送信に1分かかるため。
そこからさらに5分で、メンションとロール付与が終わる。

## どこで何が動くか

| 担当 | 動く場所 | やること |
|---|---|---|
| Apps Script | Google のサーバー | 受付番号の採番、受付メール、採択メール |
| コンテナ | スタッフのPC | Discord への投稿、承認の検知、ロール付与 |

2つに分かれているのは、Apps Script から Discord の API が呼べないため。
Discord は Bot からの通信に `DiscordBot (...)` という形の名乗りを求める。
Apps Script はこの名乗りを上書きできず、Google の固定値が送られるので、入口で拒否される。
2023年から続く制約で、回避する方法はない。

メールの送信は Apps Script が得意とするところで、パスワードを保存せずに送れる。
だから受付と連絡は Apps Script に、Discord はコンテナに置いた。

## 2つはどうやって連携するか

直接やりとりはしない。管理列に時刻を書き合って引き継ぐ。

```
Apps Script が「受付メール送信」に時刻を書く
      ↓
コンテナがその列を見て、次の処理をする
      ↓
コンテナが「承認確認」に時刻を書く
      ↓
Apps Script がその列を見て、採択メールを送る
```

列が空のときだけ処理する。両方が同じ列を書くことはない。
どちらかが止まっても、もう一方は列が埋まるのを待つだけで壊れない。

## 初めて動かすとき

この順で進める。順序が効く。

1. 3つのフォームの回答先を1つのスプレッドシートにまとめる
2. Discord の Bot を作り、サーバーに招待する (`discord_sync/README.md`)
3. Apps Script にコードを送り、`setUp` を実行する (`form_to_discord/README.md`)
4. コンテナを起動する (`discord_sync/README.md`)
5. フォームに試し送信し、受付メールとDiscord投稿が届くのを見る

管理列を作るのは 3 の `setUp` の役目。先に 4 をやると、列がそろうまでコンテナは止まる。
